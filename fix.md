# Fix: 30000ms Tool Timeout Despite Config Changes

## Where the 30000ms Timeout Comes From

The error `Error: tool call timed out after 30000ms` is generated by the guard plugin at `packages/guard/timeout-policy/src/index.ts:42`:

```ts
const message = `tool call timed out after ${timeoutMs}ms`
```

This guard **only reads each tool's declared `timeoutMs` from the tool registry**. It does not read any plugin-level configuration like `defaultTimeoutMs` or `perToolTimeouts`.

Your `unrestricted.cordis.patch.yml` correctly overrides `tool-web` (lines 94-99), but you missed two other tool plugin suites that also default to 30000ms:

| Tool Plugin | Tools | Default timeoutMs | Overridden in your patch? |
|-------------|-------|-------------------|---------------------------|
| `tool-web` | `web_fetch`, `web_search` | 30000 | ✅ Yes |
| `tool-fs-search` | `glob`, `grep` | 30000 | ❌ No |
| `tool-session-query` | `session_search`, `session_event_search` | 30000 | ❌ No |

**What you need to add:**
Edit the **live profile patch** used by your running GUI:
` /home/rakib/Desktop/deepfsdi/.dsh-isolated/profiles/web/cordis.patch.yml`

Under the `TIMEOUTS: EXTENDED FOR SLOW LOCAL MODELS` section, add these two entries:

```yaml
# ============================================================================
# FILESYSTEM SEARCH: EXTENDED TIMEOUTS
# ============================================================================
- id: tool-fs-search
  config:
    timeoutMs: 7200000

# ============================================================================
# SESSION QUERY SEARCH: EXTENDED TIMEOUTS
# ============================================================================
- id: tool-session-query
  config:
    searchTimeoutMs: 7200000
```

**Remove the useless `timeout-policy` block:** The lines 62-77 (`- id: timeout-policy` with `defaultTimeoutMs`, `perToolTimeouts`, `retryWithExtendedTimeout`) have no effect; that plugin ignores all config and only reads the tool-specific values above.

## Auto-Retry: What Exists and What Does Not

### Tool-Level Auto-Retry Does Not Exist
No built-in mechanism automatically re-runs a failed tool call. The `timeout-policy` guard only converts a timeout into an error result (`Error: tool call timed out after <ms>ms`) that the model observes. Whether to retry is the model's decision in a subsequent turn.

### LLM Request Auto-Retry (Model API Only)
The `llm-retry` plugin retries **failed model API calls**, not tool executions. Its own config is empty (`Config = Readonly<Record<string, never>>`) — any key (e.g., `enabled`, `maxRetries`) will throw `llm-retry: unknown key "enabled"` at boot.

Retry policy belongs under each **provider's** `config.retryPolicy`:

```yaml
- id: llm-your-provider  # e.g., llm-deepseek or llm-pi-ai or your custom provider
  config:
    retryPolicy:
      mode: always        # Retries every failure until success
      backoff:
        initialDelayMs: 500
        maxDelayMs: 30000
        jitterRatio: 0.1
```

Your patch already sets `mode: always` for `llm-deepseek` and `llm-pi-ai` (lines 188-204). Apply the same block to whatever provider serves your local model.

### "Ignore" Conditions Already Work
Your request to **ignore** cases where the tool:
- Stopped to ask the user something,
- Was waiting for something, or  
- Finished its job
requires **no changes**. Those cases return a normal (non-error) result, and nothing automatically retries normal results.

### No Built-in "Retry Last Task if Agent Stopped"
There is no hook to automatically re-issue the last user task if the agent loop stops. That would require session-lifecycle integration.

## Inert Settings (Can Be Removed)
These settings in your `.env.unrestricted`, `settings.unrestricted.json`, or `isolated-env.sh` are **read by nothing** and can be removed without effect:
- `TOOL_TIMEOUT_MS`, `EXTENDED_TIMEOUT_MS`, `FAST_FAIL_THRESHOLD_MS`
- `ENABLE_SMART_RETRY`, `MAX_RETRIES`, `KILL_STUCK_OPERATIONS`, `STUCK_OPERATION_THRESHOLD_MS`
- `defaultTimeoutMs`, `perToolTimeouts`, `retryWithExtendedTimeout` (under `- id: timeout-policy`)

## How to Apply
1. Edit `.dsh-isolated/profiles/web/cordis.patch.yml` with the two timeout overrides above.
2. Ensure your local LLM provider config has `retryPolicy: { mode: 'always' }`.
3. Restart the web GUI via your isolated launcher: `bash dsh-isolated.sh web`.

After restart, all six tools (`web_fetch`, `web_search`, `glob`, `grep`, `session_search`, `session_event_search`) will have a 7200000ms (2 hour) timeout budget, and the `timeout-policy` guard will no longer produce 30000ms errors.
